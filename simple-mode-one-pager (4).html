Background
Goal & Problem
Goal
Make extension authoring accessible to everyone
The Extensions Creator builder is underused — not because users don't need it, but because it exposes too much complexity at once. Platform-specific terminology, a 7-column configuration table, and a late-stage certificate signing step create a journey that most users abandon before completing. The interface was built for power users, and it shows.
Problem
Design a Simple Mode that gets anyone to a working extension
Regardless of Dynatrace experience, users should complete a working extension in a single session — without hiding capability from those who need it. The model is Data Explorer's simple/advanced toggle: one surface, two modes, connected. Simple Mode leads with the query, auto-maps metrics from parsed columns, and absorbs certificate setup silently. Advanced Mode is always one click away.

Competitor Analysis
Datadog Integrations — UX Journey

We mapped the Datadog integrations flow to understand how a best-in-class competitor handles a similar challenge: getting users from "I need to connect something" to "I have data." The persona context is a DevOps engineer who values quick discovery, flexible setup, and minimal interruptions — a more technical user than Amie, but the UX lessons transfer directly.

Step 1
Discover
Find relevant integrations quickly
Visual catalog with logos, category chips (AWS, AI/ML, Kubernetes), and a search bar. Clear separation between Installed and Available integrations. Marketplace branding ("Extend the power of Datadog") actively invites exploration. Discovery is a strength.
✅
Lesson for Simple Mode: Visual-first entry with clear status indicators removes the first layer of confusion. Dynatrace is integrated into the monitoring context but less visually prominent — Simple Mode should lead with a clear, inviting entry point.
Step 2
Context & Decision
Understand purpose, scope, and fit
Clicking a tile opens a detail page with tabs: Overview, Configure, Support, Release Notes. AWS and Azure integrations show an intro screen explaining what's supported and what setup paths are available before committing. Helps the engineer decide if the integration is relevant and feasible.
⚠️
Gap — both tools: Neither Datadog nor Dynatrace shows users what they'll get before they commit. Simple Mode's review step is an opportunity to show a preview of the metrics about to be created.
Step 3
Setup & Control
Install and configure with flexibility
Multiple setup paths: Quickstart scripts, Terraform, Manual. Inline toggles for log forwarding (90+ services) and metric/resource collection. Flexible for technical users — but potentially overwhelming without grouping. Some integrations require switching between Datadog and third-party consoles, breaking the flow.
⚠️
Gap — mirrors our problem: Datadog's console switching breaks momentum — exactly what the signing step does to our users today. Dynatrace's guided wizard is fully in-platform ✅ but offers fewer paths for automation specialists. Simple Mode addresses this by absorbing signing silently.
Step 4
Validation
Confirm the integration is working
Datadog guides the engineer to test the integration — e.g., send a webhook alert and check if it appears in Slack. Clear instructions, but the validation step is manual: the engineer must leave Datadog to confirm success. No inline confirmation or real-time status in the UI.
❌
DT advantage: Unlike Datadog, Dynatrace provides inline validation and immediate health indicators — no leaving the platform to confirm success. This is a strength to preserve and surface clearly in Simple Mode's deploy step.
Step 5
Value Delivery
Immediate benefits post-install
Auto-generated dashboards (e.g., Ruby Runtime Metrics) and IDE plugins that bring observability context directly into the developer's code editor. Rich partner ecosystem. The engineer can monitor their systems and integrate insights into daily workflows immediately after setup.
✅
DT advantage + opportunity: Dynatrace integrates directly with dashboards, alerts, and topology — stronger contextual value than Datadog's auto-provisioned dashboards. But neither tool surfaces "what next" proactively. Simple Mode's post-publish state should show users exactly where their data now appears.
5 Key Learnings for Simple Mode
1
Keep users in-platform — avoid context switching during setup and validation. Signing must be absorbed, not delegated.
2
Use visual status cues — Installed/Available, progress states, NEW badges. Users need to know where they are without reading instructions.
3
Simplify large configuration lists — group and filter to reduce overwhelm. The 7-column table is our version of Datadog's 90-toggle AWS setup.
4
Preview value early — show users what they'll get before they commit. Simple Mode's review step should show a preview of the metrics they're about to create.
5
Dynatrace's contextual advantage — unlike Datadog, extensions in Dynatrace are configurable from within any app (Logs, Infra, etc.) without navigating to a central catalog. This is a structural advantage worth amplifying in Simple Mode's post-publish state.

Research
User interviews

Run before any concepts were committed to — the goal was to understand how advanced developers work today and what less technical users would need to succeed on their own.

What the interviews confirmed is that this isn't new feedback. The friction points users described — manual column mapping, opaque terminology, the signing step arriving out of nowhere — are the same issues the product has been hearing for years. The interviews didn't surface surprises. They gave us the confidence to act on what was already known.

Reference
Inspiration — Pyramid Analytics
Pyramid Analytics — drag-and-drop field mapping into columns, rows, values, and filters
Why this matters

Pyramid Analytics solves a similar problem: users who think in data — tables, columns, values — shouldn't need to learn a tool's internal model to get value from it. Their drag-and-drop interface lets users assign fields to visual roles (Columns, Rows, Values, Filters) without understanding the underlying query structure.

The analogy for Simple Mode: a user who has a SQL query and knows what they want to measure shouldn't need to understand what a "feature set", "subgroup", or "ingest type" is. They should be able to point at a column and say — this is a number I want to track.

The Pyramid model also shows what good auto-suggestion looks like: fields are pre-typed and pre-placed, with drag to override. That's the target behaviour for our column mapping step.

Current state
The query → metrics flow today

The Polyglot TypeScript library reads the query as text and extracts column names — without running it against the database. It can see that a column is called avg_response but can't tell you it's numeric. That inference — and the mapping that follows — is currently left entirely to the user. Prototype
One approach, evolved in two phases

Simple Mode is a single approach that lives above the existing workspace — enabling users to switch between Full Builder and Simple Mode at any point. A user like Amie experiences almost the same journey as today, but in a user-friendly way. The approach evolved from a full stepper wizard covering all steps, toward a partial stepper that adapts based on the datasource the user selects — showing only the steps relevant to that source's configuration.

Phase 1
Full stepper wizard — the quick win
A mode picker modal lets users choose Simple or Full Builder on entry. Simple Mode walks through every step in a consistent wizard, regardless of datasource.
Simple Mode lives above the existing workspace. The mode picker appears when creating a new extension — users can switch between Full and Simple at any point. The wizard covers: datasource selection → extension name → query setup → certificate → review & deploy. Each step is self-contained, with no exposed YAML and no platform terminology. Certificate setup is absorbed silently for new users.
This approach surfaced a key insight: not all datasources need the same steps → which led to Phase 2
Phase 2
Partial stepper — adapts to the datasource
The wizard now changes based on what datasource the user selects. A SQL source shows the query editor and column mapping. Other sources show only the steps relevant to their configuration.
For SQL datasources: the split-pane layout keeps the query visible on the left while columns are auto-detected and pre-assigned on the right — Metric or Dimension, confirmed with a single toggle. The live summary bar at the bottom gives instant feedback. The interval picker is inline. For non-SQL datasources, the query step is replaced by the appropriate configuration — keeping the same wizard shell but with context-aware content at each step.
